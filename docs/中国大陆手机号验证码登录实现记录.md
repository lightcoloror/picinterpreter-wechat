## 变动 1：在照护管理账号页增加短信登录

- **意图：** 让图语家微信用户在不复制 CBoard 账号系统的前提下，使用已绑定的中国大陆手机号进入账号同步。
- **决策：** 账号面板保留邮箱登录和注册，并增加短信验证码登录模式；请求与确认统一使用 purpose=`login`，成功后调用 `CboardAccountPort.loginWithPhone`。
- **理由：** 微信只是新的客户端，身份、JWT、Settings 和板数据仍应来自同一个 cboard-api；这样不会产生“小程序账号”和“CBoard 账号”两套数据。
- **证据：** `cboardAccountPort` 测试覆盖公开能力、purpose、手机号登录端点和标准 session 解析；账号与同步相邻回归 `5 files / 41 tests` 全部通过。
- **生效范围：** management 分包账号页。未登录用户的患者表达、接收、朗读、分词、图片和本地历史不受影响。

## 变动 2：复用登录后的账号合并流程

- **意图：** 保证手机号与密码登录后看到相同的图语家数据，避免两种登录方式形成不同恢复行为。
- **决策：** 抽取并复用现有 `completeAccountLogin` / `runAccountLogin`；两种登录都保存同一种 CBoard session，再执行相同的公开数据拉取和本地/云合并。
- **理由：** 认证方式只决定如何取得 session，不应改变 Board、Settings、接收记录和常用语合并语义。
- **证据：** `accountMerge`、`cboardSession`、`communicationCloudSync` 与 management 测试和 `cboardAccountPort` 同组回归全部通过。
- **生效范围：** 微信账号登录后的 session 与同步。验证码、原始手机号和短信供应商密钥不进入微信 storage。

## 变动 3：保持小程序包体和平台边界

- **意图：** 增加账号入口时继续满足微信小程序性能与代码质量要求，不把 Web UI 或第二套认证 SDK 打入主包。
- **决策：** 只增加纯 TypeScript port 和现有 Taro 表单胶水，不引入 Better Auth、SuperTokens、React DOM 或 Material UI；账号功能继续留在 management 分包，组件按需加载配置保持不变。
- **理由：** CBoard API 已承担验证码、限流和 Session，微信端无需携带认证基础设施。保持分包可以控制主包启动成本。
- **证据：** TypeScript、完整 ESLint、`186 app / 29 CBoard core` 边界检查和微信 production build 通过；主包 `1,249,564 B`，低于 1.5 MiB 建议线并保留 `323,300 B` 余量，management 分包 `498,590 B`，其他分包也低于建议线。
- **生效范围：** 微信源码、management 分包和 production 构建门。WechatSI 插件大小仍需在上传前用微信开发者工具官方性能扫描确认；本轮没有调用开发者工具。

## 变动 4：保留真实运营门

- **意图：** 防止代码存在但后端未配置时仍向用户显示“短信登录可用”。
- **决策：** UI 依赖 cboard-api 公开 `phoneLoginAvailable`；未配置时显示安全降级并保留邮箱登录。真实手机登录必须在腾讯云短信、API 公网 HTTPS、微信 request 合法域名和已有手机号账号均准备后验收。
- **理由：** 小程序不能自行发送可信短信，也不能绕过微信网络域名和后端密钥边界。
- **证据：** 能力配置、失败映射和登录 session 均有 port 测试；当前没有真实短信或公网部署证据，三端全量测试也未在当前机器的时间边界内返回汇总，因此不冒充生产验收完成。
- **生效范围：** 发布前检查与状态文案。旧账号未绑定手机号时继续使用邮箱密码或 OAuth；管理员不允许仅凭短信登录。
